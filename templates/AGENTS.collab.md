## 项目文档与阅读顺序

- 开始工作前用 `planning-with-files-zh` 的 `resume-context`，读 `docs/project/STATUS.md` 与明确绑定的任务 PLAN / PROGRESS / FINDINGS；其余长期文件按需读。
- `docs/project/` 是目标、范围、决定、路线及任务状态的唯一长期语义来源。权威顺序：用户最新明确指令 > accepted 决定 > accepted 目标与路线 > 活动任务 PLAN > 代码与测试事实 > 代理建议与缓存。
- 多个活动任务须明确 bind，不能猜最近任务。

## 一事一处

每个事实只在下表的一个位置写全，其他位置只放编号或链接，不复述数字和经过。

| 内容 | 唯一位置 | 写法与上限 |
|---|---|---|
| 实验数字、经过、限制 | 报告与任务 evidence | 一次写全 |
| 任务当前状态 | 任务 PROGRESS | 覆盖式：只有“当前状态 / 未决问题 / 最近验证 / 自修记录”四节，合计不超过 40 行；时间线由 git 与 `events.jsonl` 提供 |
| 局部发现 | 任务 FINDINGS | 每条一句话加证据指针 |
| 跨任务发现 | FINDINGS | 每条一句话结论、证据指针、后续影响，不写数字细节 |
| 决定 | DECISIONS | 标题一句话（不超过 60 字）；正文：决定要点、用户原话、取代关系 |
| 当前阶段与下一步 | STATUS | 当前摘要、最近 3 条验证（每条一行）、下一步 |
| 规格 | `<交接目录>` 说明文件 | 只写规格；裁定写进 DECISIONS，说明文件只加一行链接 |
| 提交 | git | 见“提交” |

- 工具保证：机械记录（接管、同步、状态变化、对账）写进任务目录 `events.jsonl`；`lint-records` 检查长度、数字重复、已结项任务的决定仍在 DECISIONS（L7）与条目堆积（L8），并入 `validate --strict` 的 warnings；`complete` 的输出 `archive_reminders` 列出本任务该归档的决定。
- 结项对账只改：任务 PLAN 状态、FINDINGS 一条、STATUS 的“最近验证”一行与“下一步”、需要时 DECISIONS 一条；`<交接目录>` 的 README 删一行。
- 归档：`docs/project/archive/` 下 status-log、decisions-archive、findings-archive 三个只追加文件，非 canonical，恢复时不默认读。结项任务的立项、恢复、样本与费用裁定在结项时移入归档并在 HISTORY 索引；仍约束后续工作的决定在条目里加一行 `- Keep: 原因`。编号与用户原话不变，归档不等于撤回；当天最新的决定与发现编号须留在 canonical 文件中，以免 CLI 重号。

## 写入权限与交接

**<规划者>**
- 维护长期规划文件（PROJECT、ROADMAP、DECISIONS、FINDINGS、STATUS、HISTORY、归档）、README、AGENTS.md、CLAUDE.md、`<交接目录>`。
- 用 `start-task` 建任务，写任务规格：PLAN 的目标、验收条件、关联决定。
- 审阅交付、项目对账、运行 `complete`，记录用户决定。

**<执行者>**
- 维护代码、脚本、测试、依赖锁、报告；任务的 PROGRESS、FINDINGS、evidence；PLAN 的执行部分（阶段勾选、当前阶段）。有证据的验收项才勾选，不改目标与验收条件的文字。
- 流程：`bind-task` → 实施 → `ready-for-review`。不运行 `complete`，不改规划者文件；`pre_tool` hook 按 `tools/codex/project-policy.json` 拒绝越界修改。

**交接**
- 给执行者的材料放在 `<交接目录>`，入口是其中的 README.md。一个任务一份说明文件，README 只列当前任务；结项后说明文件移入其 `archive/`。
- 通信经 bridge：<规划者> 用 `send_to_codex`（目标 `thread_id`），<执行者> 用 `send_to_claude`（目标 `session_id`）。
- **消息只是通知，文件才是依据**。每条不超过 10 行：

  ```
  [类型] 任务号 · 版本
  指针：文件路径#小节（必填）
  一句话：……
  需要对方：……（可省略）
  ```

  类型：`HELLO`（任一方：我换了新对话）、`BRIEF`（规划者：说明文件就绪）、`QUESTION`（执行者：需规划者决定，已写在 PROGRESS“未决问题”）、`VERDICT`（规划者：裁定已落文件）、`READY`（执行者：已 ready-for-review）、`BLOCKED`（执行者：已 block-task）。不粘贴报告、日志或数字表。送达不等于已读，状态以规划 CLI 为准。
- **换对话与寻址**：
  - 端点登记在本机 `.runtime/bridge-endpoints.json`（git 忽略）：`planner` 是规划会话的 `session_id`，`executors` 按任务号记执行对话的 `thread_id`。不在 canonical 文件里写会话编号。
  - 回复一律回给来信经验证的来源编号。主动发起先读登记；发送失败时不按标题或目录猜收件人，把内容留在文件里，等对方新对话读到。
  - 新对话自动绑定：新开的对话开始工作时自己完成绑定。<规划者>：`resume-context` 后查登记的 `planner`，原对话不活跃或就是自己，就把自己写进去并向 `executors` 发 `HELLO`；原对话正在执行就先问用户。<执行者>：找出没有活跃执行对话的活动任务，只有一个就 `bind-task --bridge-thread-id <本对话>`（绑过的用 `takeover-task`），确认绑定成功后发 `HELLO`。
  - 【需用户授权】新任务开新对话：<规划者> 发新任务的 `BRIEF` 时写明“请新开一个对话执行并 `bind-task` 本任务”。收到这样的 BRIEF，<执行者> 就新开对话、在新对话里绑定，由新对话回 `HELLO`；原对话不改名，也不接新任务。
  - 多对话并行：由一个执行对话担任通信对话，分派、监控并汇总；`executors` 里这些任务都登记通信对话的编号，其他执行对话不与规划者通信。

**问题升级的三级处理**
1. **<执行者> 自修一次**：不改变规格语义的实现问题直接修，用回归测试或离线重放证明，PROGRESS“自修记录”写一行。不得放宽门槛或停止条件；同一问题只自修一次。
2. **仍不行 → <规划者> 自动审阅**：<执行者> 在 PROGRESS“未决问题”写清现象、试过什么、建议，发 `QUESTION`。<规划者> 不等用户，读文件、复核并裁定，写进说明文件新小节，发 `VERDICT`。只处理同一方法内的修正，结项时一并写进交付说明。
3. **必须用户确认**：下列情形 <规划者> 不得自行裁定，先停下问用户，确认后才发 `VERDICT`：
   - 要换一种方法或方案才能继续；
   - 当前路线走不通；
   - 思路、方向、目标、验收条件或评测口径变化；
   - 规格外新增费用、实际累计将超过上限、重跑已完成的付费单元；
   - 新增依赖、需要启动影响本机的进程；
   - 任何要写成 accepted 的决定。
- 被阻塞时 <执行者> 运行 `block-task --reason` 并发 `BLOCKED`。
- <规划者> 自动审阅时同样遵守写入边界，不替 <执行者> 改代码。

**提交**
- <执行者> 在 `ready-for-review` 时提交执行产物；双方的提交都只包含各自的文件。
- 标题：`版本号 任务号或“规划” 一句话`，不超过 72 字；正文可选，最多 5 行，只写文件指针。
- 规划提交的频率：一个任务期间的多次裁定不逐条提交，文件照常即时写好（<执行者> 读的是工作区文件，不依赖提交），攒到该任务结项时与对账合成一次提交。只有重大方向性决定，或涉及后续规划的改动（立项派发、路线或阶段顺序变化、协作规则变化）才单独提交。
